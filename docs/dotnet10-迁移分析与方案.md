# .NET 10 迁移分析与方案

> 结论先行：**需要迁移，目标 .NET 10 LTS。建议近期直接迁移，不必等 .NET 11，也不必过渡到 .NET 8/9。**
> （net7 早在 2024-05-14 就已 EOL，不存在"赶在某个日期前迁完"的期限；2026-11-10 是 .NET 8/9 的 EOL，
> 只说明"过渡到 8/9 没有价值"。）
> 本文档只做分析与方案；执行时按 §3.1 的顺序操作。
>
> 分析日期：2026-09-13　|　数据来源：微软官方支持策略页 + 本机实测
> 修订：v1.5 初稿 → **v1.6 按第五轮评审意见修订**（见 §1.0），并补入 CI 流水线这一迁移面

| 14 | 流程简化为 12 步 | ✅ | §3.1 已重写 |

**本轮评审之外的新发现（影响迁移面的重要事实）：**
`.github/workflows/release.yml` 把 SDK 钉在 `dotnet-version: 7.0.x`。TFM 改成 net10 后，
**SDK 7 无法构建 net10 目标，CI 必挂**。所以迁移面是 **4 处**：3 个 csproj 的 TFM + 1 个 workflow 的 SDK 版本，
外加需要补提交的 `docs/`。

## 1. 现状盘点（全部为实测，非推断）

### 1.1 工具链与运行时

| 项 | 实测值 | 说明 |
|---|---|---|
| 已装 SDK | 仅 `7.0.410` | **没有** .NET 10 SDK，必须先装 |
| 官方最新 .NET 10 SDK | **`10.0.401`**（2026-09-08，含 Runtime 10.0.12、C# 14） | `global.json` 要写这个完整版本号 |
| 已装运行时 | `MicrosoftWindowsDesktop.App` 7.0.20 / 8.0.8 / **10.0.11** | 安装 SDK 10.0.401 后会**同时带上 10.0.12**（SDK 自带匹配的运行时） |
| dotnet Host | 10.0.11 | 宿主本身已是 10 |
| winget | v1.29.290 可用 | 可用于安装 SDK |
| 当前 shell 权限 | 非管理员 | 安装机器级 SDK 时会弹一次 UAC |

### 1.2 三个工程的目标框架

| 工程 | TFM | 类型 | 依赖 |
|---|---|---|---|
| `FocusGuard.Core` | `net7.0` | 类库（全部业务逻辑） | 无 |
| `FocusGuard.App` | `net7.0-windows` | WPF 界面（`UseWPF`） | 仅 `ProjectReference` → Core |
| `FocusGuard.Tests` | `net7.0` | 控制台测试宿主 | 仅 `ProjectReference` → Core |

### 1.3 发布面（两条路径，形态不同）

| 路径 | 触发 | 形态 | 说明 |
|---|---|---|---|
| 本地 `dist\` | 手动 `dotnet publish -o dist` | **框架依赖** | 目标机器需要 .NET 10 桌面运行时 |
| GitHub Actions `release.yml` | push `v*` 标签 | **自包含 win-x64**（`--self-contained true`） | 产物自带运行时，zip 上传到 GitHub Release |

迁移对两者都**只改 SDK/TFM，不动发布形态** —— 一次迁移只改一个变量。

### 1.3 依赖面（本次分析最重要的一个事实）

`project.assets.json`（NuGet 还原的实际结果）里**只有** `FocusGuard.Core/1.0.0` 这一项 ——
也就是说：

- **零第三方 NuGet 包**。没有 xunit/NUnit、没有 Newtonsoft、没有任何外部库；
  `System.Text.Json`、文件 IO、WPF 全部来自共享框架本身
- 没有中央包管理（`Directory.Packages.props`）、没有 `global.json`、没有 `nuget.config`
- 构建只依赖 SDK 自带的 targeting pack

**结论：第三方库兼容性这个迁移风险的最大类别，在本项目整体不存在。**

### 1.4 其他相关事实

- **项目已在 git 仓库中**（`main` 分支，`.gitignore` 已覆盖 `bin/`、`obj/`、`dist/`、`.vs/`，
  上述目录均未被跟踪）→ 回滚方案可以正常依赖 git。**注意 `docs/` 目前处于未跟踪状态**，
  迁移文档应先补提交
- 代码对外部世界的接触面：文件 IO（hosts / 状态文件 / DACL）、外部进程（`icacls` / `ipconfig` / `whoami`）、
  WPF 单窗口。**没有**注册表读写、没有网络服务端、没有数据库
- 当前基线：构建 0 警告 0 错误、49/49 测试通过
- **CI 迁移面**：`.github/workflows/release.yml` 中 `actions/setup-dotnet@v4` 钉了 `dotnet-version: 7.0.x`，
  必须与 TFM 同步改为 `10.0.x`，否则打标签发版时 CI 必挂

## 2. 必要性评估

### 2.1 支持周期（微软官方数据）

| 版本 | 类型 | 支持阶段 | 终止支持 | 相对现在 |
|---|---|---|---|---|
| **.NET 7** | STS | 已结束 | **2024-05-14** | **已过期 28 个月** |
| .NET 8 | LTS | **维护期**（仅安全补丁） | **2026-11-10** | **60 天后** |
| .NET 9 | STS | 维护期 | 2026-11-10 | 60 天后 |
| **.NET 10** | **LTS** | **活动**（最新 10.0.12，2026-09-08） | **2028-11-14** | **还有 27 个月** |
| .NET 11 | STS | RC1（2026-09-08） | — | 尚未 GA |

（来源：`dotnet.microsoft.com/platform/support/policy/dotnet-core` 与微软生命周期页）

**两条硬结论：**
1. net7.0 已经超过支持期 28 个月，期间的所有安全补丁都拿不到；
2. **迁到 .NET 8 或 9 是负迁移** —— 它们 60 天后就同时到期，等于白做一次迁移。

### 2.2 不迁移的后果（诚实分层，不夸大）

| 层面 | 后果 | 严重度 |
|---|---|---|
| 安全补丁 | 运行时与 BCL 的已知漏洞不再修复。本项目**以管理员运行、会改写系统文件（hosts）**，属于高权限工具，运行时漏洞的实际意义比普通应用大 | 中 |
| 构建体验 | 用新 SDK 构建 `net7.0` 会持续报 `NETSDK1138`（目标框架已停止支持）；未来 SDK 可能进一步收紧 | 低 |
| 语言与工具 | 停留在 C# 11（net10 默认 C# 14），新语法、新分析器、新 SDK 特性都用不上 | 低 |
| 排查成本 | 文档、资料、社区答案都在往前走，遇到问题越往后越难找到对应版本的资料 | 低 |
| 长期维护 | 每次 .NET 大版本更新都要"再评估一次"，欠的债会滚 | 中 |

**必须诚实说明的另一面**：这是单机个人工具，没有网络暴露面，实际被利用的概率**不等于零但不高**。
所以"必须迁移"的论据并不是"马上会出事"，而是一个悬殊的成本收益比：

> **成本 = 3 行 TFM 改动 + 一轮完整验证（约 1.5 小时）；收益 = 27 个月的安全支持 + 与本机运行时对齐。**

### 2.3 迁移的实际收益

1. 安全支持到 **2028-11-14**（+27 个月）
2. C# 11 → C# 14（本次不主动改语法，但解锁后续演进）
3. 与本机已装的 10.0.11 运行时对齐，不必再为一个旧 TFM 保留 7.0.20 桌面运行时
4. 新 SDK 构建 `net7.0` 时的 EOL 警告消失
5. WPF 自 .NET 7 以来的修复与改进

### 2.4 "完整迁移"是否必要？

**是，且三个工程必须一起迁**。理由：

- `App(net10.0-windows)` 技术上可以引用 `net7.0` 的 Core（低版本 TFM 程序集能在高版本运行时上跑），
  但那会留下一个**混合状态**：Core 仍是 EOL 的 net7.0，构建警告照旧，等于只做了一半
- 三个工程的代码量总共约 1100 行，一起迁的边际成本接近于零
- `Tests` 是测试门禁，它若停在 net7.0，"迁移后验证"就没有意义

## 3. 迁移方案

### 3.0 迁移前准备

| # | 动作 | 说明 |
|---|---|---|
| P1 | 确认 git 基线：`main` 上已有 3 个提交；**把未跟踪的 `docs/` 补提交**；建 `migration/net10` 分支 | 项目**已经在 git 中**（`.gitignore` 已覆盖 `bin/`、`obj/`、`dist/`、`.vs/`，且这些目录未被跟踪），回滚方案可以正常依赖 git |
| P2 | 安装 .NET 10 SDK：`winget install Microsoft.DotNet.SDK.10`（约 200MB，会弹一次 UAC） | **保留 7.0.410 不卸载**，这是回滚的前提；安装后 `dotnet --list-sdks` 应同时出现两者，且 `dotnet --list-runtimes` 出现 Desktop 10.0.12（SDK 自带） |
| P3 | 记录迁移前基线：0 警告构建、49/49 测试、`--diag` 输出各留一份 | 基线要在**换 SDK 之前**取，否则就不是 net7 的基线了 |

（不再"迁移前先钉 7.0.410 的 global.json"：机器上本来就只有这一个 SDK，环境无歧义，
多加一个马上要改的文件只会污染 diff。）

### 3.1 执行顺序（clean-room，最小 diff）

| # | 动作 | 通过判据 | 失败时 |
|---|---|---|---|
| S1 | 建分支 `migration/net10` | `git branch --show-current` | —— |
| S2 | 安装 .NET 10 SDK（若尚未装） | `dotnet --list-sdks` 同时出现 `7.0.410` 与 `10.0.401`；`--list-runtimes` 出现 Desktop 10.0.12 | —— |
| S3 | 新建 `global.json`（注意：**必须写完整版本号，不支持通配符**） | `dotnet --version` = `10.0.401` | —— |
| S4 | 改 4 处 TFM/SDK：三处 csproj 的 TFM（`net7.0`→`net10.0`、`net7.0-windows`→`net10.0-windows`）**+ `.github/workflows/release.yml` 的 `dotnet-version: 7.0.x` → `10.0.x`** | —— | 纯文本改动，git 即时回退 |
| S5 | **删除所有 `bin/`、`obj/`、`dist/`**（不能用 `dotnet clean` 代替：TFM 变了，clean 清不掉旧 `net7.0` 的输出目录） | 目录已不存在 | —— |
| S6 | `dotnet restore` + `dotnet build FocusGuard.sln -c Release` | **0 警告 0 错误** | 逐条处理新警告；2 小时定位不了就回滚 |
| S7 | 全量测试 `dotnet run --project tests/FocusGuard.Tests -c Release` | **49/49 通过** | 不通过不进入下一步 |
| S8 | `dotnet publish src/FocusGuard.App -c Release -o dist`（**先删掉旧 dist，全新生成**） | 见 §3.4 L3 的功能性验证 | —— |
| S9 | CLI 冒烟：`dist\FocusGuard.exe --diag`（只读） | 输出 `状态文件：可用`、`实际强制措施：无`、hosts 无区块 | —— |
| S10 | **WPF 手动验收 10 项**（按《验收与升级作业单.md》，重点：窗口尺寸 / DPI / 字体 / 圆角 / Hover / 图标 / UAC / 启动路径） | 全部通过 | 记录现象与日志，反馈后定位 |
| S11 | 提交迁移改动 | **git diff 里应只有：3 个 csproj、1 个 workflow、`global.json`、相关文档**。若出现成片的 `.cs` 改动，说明掺入了不必要的重构，要拆出来 | —— |
| S12 | 合并回 `main`；**至少保留 7.0.410 两到四周**再考虑卸载 | —— | —— |

> `global.json` 写法（**不支持 `10.0.x` 通配符，必须完整版本号**；SDK 号与运行时号是两套，别混）：
> ```json
> { "sdk": { "version": "10.0.401", "rollForward": "latestPatch", "allowPrerelease": false } }
> ```
> 安装更新的 SDK 补丁后，把这里的版本号跟着改即可。

### 3.2 可能的破坏性变更与应对

| 类别 | .NET 7 → 10 的变化 | 本项目是否受影响 | 应对 |
|---|---|---|---|
| **语言版本** | 默认 C# 11 → C# 14，新编译器/分析器可能报出新警告 | **可能**（本项目把 0 警告当门禁） | 逐条评估：真问题就修，误报就用注释说明原因后局部抑制；不允许整批压制 |
| **迁移纪律** | —— | **是** | 迁移提交里**不要顺手使用 C# 14 新语法**（`field`、`extension`、集合表达式等），否则出 Bug 时分不清是框架迁移问题还是代码重构问题。最小 diff 是纪律，不是洁癖 |
| **WPF** | .NET 9 起 WPF 引入新的 Fluent 主题（可选启用），默认主题行为未变 | 间接可能（本项目**全部使用自绘 ControlTemplate + 显式颜色**，不依赖默认主题细节） | S10 手动验收重点看：窗口尺寸、DPI scaling、字体、圆角、按钮 Hover/Pressed、图标、UAC、启动路径 |
| **BCL 文件 IO** | `File.Replace` / `File.Move(overwrite:)` / `WriteAllBytes` / `GetFolderPath` 语义稳定 | 无 | D1–D4、B1 测试守住 |
| **`System.Text.Json`** | 跨版本有微调（转义、属性顺序等） | 低（只序列化自有 POCO，消费方也是自己） | F2/F3 往返测试守住 |
| **外部进程** | `icacls` / `ipconfig` / `whoami` 与 .NET 版本无关 | 无 | C/G 组测试守住 |
| **Windows 特定** | UAC manifest、apphost、`SpecialFolder.System` 行为稳定 | 无 | —— |
| **部署面** | 本地 `dist`（框架依赖）需要 .NET 10 桌面运行时；**CI 产物是自包含 win-x64，自带运行时** | 本地分发（换机器）时是 | 两条路径形态都**保持不变**，迁移只改 SDK/TFM |
| **状态/配置文件** | `state.json` / `config.json` 与 TFM 无关 | 无 | 无需迁移 |
| **CI** | workflow 钉的 SDK 版本决定能否构建新 TFM | **是**（`release.yml` 钉 `7.0.x`） | S4 同步改为 `10.0.x`；打 `v*` 标签前先在分支上确认 CI 通过 |
| **SDK 行为** | `NETSDK1138` 警告消失；新 SDK 分析器更严格 | 可能（新警告） | 同语言版本项 |

### 3.3 依赖包与第三方库兼容性

- **零第三方 NuGet 依赖（实测证据见 §1.3）** → 这一类风险整体不存在，是本方案最确定的利好
- 唯一的外部依赖是 SDK 自带的 targeting pack 与 `Microsoft.WindowsDesktop.App` 共享框架 → 本机已有 10.0.11
- 测试宿主是自研的无依赖控制台 → 不存在 xunit/NUnit/MSTest 的版本升级连锁问题
- 未来若引入第三方包，需在引入时确认其 `net10.0` 支持，而不是留到下次迁移

### 3.4 测试与验证策略（六层，逐层放行）

| 层 | 内容 | 判据 | 不通过时 |
|---|---|---|---|
| L1 | 构建 | 0 警告 0 错误 | 逐条处理警告，禁止整批压制 |
| L2 | 49 项测试（纯逻辑 + 真实 icacls/文件系统集成） | 全部通过 | 定位根因后修复；这是迁移的门禁 |
| L3 | **发布功能性验证**（替代原来的"与 bin/Release SHA256 一致"——publish 输出与 build 输出本就不保证字节一致，不能当通用门禁）：<br>① `dist` 是**全新生成**的目录（先删后建）；② `dist\FocusGuard.runtimeconfig.json` 里 TFM 为 `net10.0`、依赖 `Microsoft.WindowsDesktop.App 10.x`；③ `FocusGuard.Core.dll` 存在；④ 图标 8 帧仍在 exe 中；⑤ 关键文案（如"无法留下恢复线索"）存在 | 全部满足 | 查 publish 参数 |

| L5 | **WPF 手动验收 10 项**（见作业单；重点：窗口尺寸 / DPI / 字体 / 圆角 / Hover / 图标 / UAC / 启动路径） | 全过 | 记录现象 + 日志，反馈定位 |
| L6 | 虚拟机硬断电（可选，独立事项） | —— | 不阻塞本次迁移 |

另加一条 **CI 验证**：把 `v*` 标签打在一个测试提交上（或先改 workflow 只跑 build 不发版），
确认 Actions 上 .NET 10 构建通过——这能提前暴露"本机 OK、CI 挂掉"的差别。

### 3.5 回滚方案

**触发条件**：S6–S10 任一层失败，且 2 小时内无法定位根因 → 回滚，问题另行处理。
回滚本身不承担"修好"的义务，先恢复可用基线。

| 场景 | 操作 |
|---|---|
| **首选（git 已就位）** | `git switch main`（或 `git revert` 迁移提交）→ 删除 `bin`/`obj`/`dist` → 重建 → 49 项测试确认回到基线 |
| **只回滚 SDK 选择** | 把 `global.json` 的版本改回 `7.0.410` → 重建（TFM 已是 net10 时**不能**只做这一步，必须连同 TFM 一起回） |
| **完整回滚（代码+TFM+CI）** | 三处 TFM 改回 `net7.0` / `net7.0-windows` + workflow 改回 `7.0.x` → 删除 `bin`/`obj`/`dist` → 重建 → 49/49 测试 → 重新 publish |
| **数据回滚** | 不需要。`state.json` / `config.json` / hosts 的形态与 TFM 无关 |
| **前提** | **7.0.410 必须保留**（这就是回滚能力本身），至少保留到迁移稳定后 2–4 周 |

### 3.6 风险评估矩阵

| 风险 | 概率 | 影响 | 缓解手段 |
|---|---|---|---|
| 新编译器/分析器产生新警告 | 中 | 低 | 0 警告门禁；逐条评估，禁止整批压制 |
| WPF 观感/行为差异 | 低 | 低 | 全部自绘模板 + 显式颜色；S10 手动验收确认 |
| 49 项测试出现回归 | 低 | 中 | 测试本身就是迁移门禁，先修再走 |
| **CI 漏改导致发版挂掉** | 中（不补就是必然） | 中 | 迁移面清单包含 `release.yml`；发 `v*` 标签前先验证 CI |
| 换机器分发缺运行时 | 中 | 中 | 本地 `dist` 为框架依赖，文档写明需 .NET 10 桌面运行时；CI 产物是自包含、无此问题 |
| 图标/资源嵌入变化 | 低 | 低 | L3 功能性验证含图标 8 帧检查 |
| 第三方包不兼容 | **不存在** | — | 零依赖（§1.3 实测） |
| 回滚不可用 | 低 | 高 | git 已就位 + 保留 7.0.410 |
| 中断（断电等）导致半迁移 | 低 | 低 | TFM 是 3 处纯文本改动 + 1 处 workflow，重跑构建即可发现；无持久化副作用 |

**总体评价：低风险迁移。** 不确定性最集中的是 WPF 观感与 CI，分别靠"最小 diff + 手动验收"
和"迁移面清单显式包含 workflow"兜底；最大的不确定来源（第三方依赖）恰好不存在。

## 4. 如果想缓一缓：不迁的替代路径

| 路径 | 评价 |
|---|---|
| **A. 保持 net7.0，接受 EOL** | 可行，但要写进已知边界（当前文档已写）。问题不会恶化，也不会好转；每过一个大版本就要重新评估一次 |
| **B. 迁到 .NET 8 LTS** | **不推荐**：60 天后（2026-11-10）就到期，等于白做一次迁移还得再做一次 |
| **C. 迁到 .NET 9 STS** | 同 B，且 STS 支持期更短 |
| **D. 迁到 .NET 10 LTS（推荐）** | 支持到 2028-11-14；本机运行时已就位；零依赖使成本最低 |

**结论：要迁就直接迁 .NET 10，不要在 8/9 上停留。**
