# .NET 10 迁移分析与方案

> 结论先行：**需要迁移，目标 .NET 10 LTS，且宜在 2026-11-10 之前完成**。
> 本项目迁移成本极低的根本原因是：**零第三方 NuGet 依赖** —— 迁移风险最大的那一类问题在这个项目里根本不存在。
> 本文档只做分析与方案，未修改任何代码或配置。
>
> 分析日期：2026-09-13　|　数据来源：微软官方支持策略页 + 本机实测

---

## 1. 现状盘点（全部为实测，非推断）

### 1.1 工具链与运行时

| 项 | 实测值 | 说明 |
|---|---|---|
| 已装 SDK | 仅 `7.0.410` | **没有** .NET 10 SDK，必须先装 |
| 已装运行时 | `MicrosoftWindowsDesktop.App` 7.0.20 / 8.0.8 / **10.0.11** | .NET 10 桌面运行时**已经在机器上**，迁移后无需另装运行时 |
| dotnet Host | 10.0.11 | 宿主本身已是 10 |
| winget | v1.29.290 可用 | 可用于安装 SDK |
| 当前 shell 权限 | 非管理员 | 安装机器级 SDK 时会弹一次 UAC |

### 1.2 三个工程的目标框架

| 工程 | TFM | 类型 | 依赖 |
|---|---|---|---|
| `FocusGuard.Core` | `net7.0` | 类库（全部业务逻辑） | 无 |
| `FocusGuard.App` | `net7.0-windows` | WPF 界面（`UseWPF`） | 仅 `ProjectReference` → Core |
| `FocusGuard.Tests` | `net7.0` | 控制台测试宿主 | 仅 `ProjectReference` → Core |

### 1.3 依赖面（本次分析最重要的一个事实）

`project.assets.json`（NuGet 还原的实际结果）里**只有** `FocusGuard.Core/1.0.0` 这一项 ——
也就是说：

- **零第三方 NuGet 包**。没有 xunit/NUnit、没有 Newtonsoft、没有任何外部库；
  `System.Text.Json`、文件 IO、WPF 全部来自共享框架本身
- 没有中央包管理（`Directory.Packages.props`）、没有 `global.json`、没有 `nuget.config`
- 构建只依赖 SDK 自带的 targeting pack

**结论：第三方库兼容性这个迁移风险的最大类别，在本项目整体不存在。**

### 1.4 其他相关事实

- **项目不在 git 仓库中**（`git rev-parse` 失败）→ 回滚方案不能依赖版本控制，必须先补上
- 代码对外部世界的接触面：文件 IO（hosts / 状态文件 / DACL）、外部进程（`icacls` / `ipconfig` / `whoami`）、
  WPF 单窗口。**没有**注册表读写、没有网络服务端、没有数据库
- 当前基线：构建 0 警告 0 错误、49/49 测试通过、`dist` 与源码产物 SHA256 一致

## 2. 必要性评估

### 2.1 支持周期（微软官方数据）

| 版本 | 类型 | 支持阶段 | 终止支持 | 相对现在 |
|---|---|---|---|---|
| **.NET 7** | STS | 已结束 | **2024-05-14** | **已过期 28 个月** |
| .NET 8 | LTS | **维护期**（仅安全补丁） | **2026-11-10** | **60 天后** |
| .NET 9 | STS | 维护期 | 2026-11-10 | 60 天后 |
| **.NET 10** | **LTS** | **活动**（最新 10.0.12，2026-09-08） | **2028-11-14** | **还有 27 个月** |
| .NET 11 | STS | RC1（2026-09-08） | — | 尚未 GA |

（来源：`dotnet.microsoft.com/platform/support/policy/dotnet-core` 与微软生命周期页）

**两条硬结论：**
1. net7.0 已经超过支持期 28 个月，期间的所有安全补丁都拿不到；
2. **迁到 .NET 8 或 9 是负迁移** —— 它们 60 天后就同时到期，等于白做一次迁移。

### 2.2 不迁移的后果（诚实分层，不夸大）

| 层面 | 后果 | 严重度 |
|---|---|---|
| 安全补丁 | 运行时与 BCL 的已知漏洞不再修复。本项目**以管理员运行、会改写系统文件（hosts）**，属于高权限工具，运行时漏洞的实际意义比普通应用大 | 中 |
| 构建体验 | 用新 SDK 构建 `net7.0` 会持续报 `NETSDK1138`（目标框架已停止支持）；未来 SDK 可能进一步收紧 | 低 |
| 语言与工具 | 停留在 C# 11（net10 默认 C# 14），新语法、新分析器、新 SDK 特性都用不上 | 低 |
| 排查成本 | 文档、资料、社区答案都在往前走，遇到问题越往后越难找到对应版本的资料 | 低 |
| 长期维护 | 每次 .NET 大版本更新都要"再评估一次"，欠的债会滚 | 中 |

**必须诚实说明的另一面**：这是单机个人工具，没有网络暴露面，实际被利用的概率**不等于零但不高**。
所以"必须迁移"的论据并不是"马上会出事"，而是一个悬殊的成本收益比：

> **成本 = 3 行 TFM 改动 + 一轮完整验证（约 1.5 小时）；收益 = 27 个月的安全支持 + 与本机运行时对齐。**

### 2.3 迁移的实际收益

1. 安全支持到 **2028-11-14**（+27 个月）
2. C# 11 → C# 14（本次不主动改语法，但解锁后续演进）
3. 与本机已装的 10.0.11 运行时对齐，不必再为一个旧 TFM 保留 7.0.20 桌面运行时
4. 新 SDK 构建 `net7.0` 时的 EOL 警告消失
5. WPF 自 .NET 7 以来的修复与改进

### 2.4 "完整迁移"是否必要？

**是，且三个工程必须一起迁**。理由：

- `App(net10.0-windows)` 技术上可以引用 `net7.0` 的 Core（低版本 TFM 程序集能在高版本运行时上跑），
  但那会留下一个**混合状态**：Core 仍是 EOL 的 net7.0，构建警告照旧，等于只做了一半
- 三个工程的代码量总共约 1100 行，一起迁的边际成本接近于零
- `Tests` 是测试门禁，它若停在 net7.0，"迁移后验证"就没有意义

## 3. 迁移方案

### 3.0 迁移前准备

| # | 动作 | 说明 |
|---|---|---|
| P1 | **建立版本控制**：`git init` + 初始提交 + 建 `migration/net10` 分支 | 项目当前**不在 git 中**，这是回滚方案的基石。最低限度也要做一次整目录备份（排除 `bin`/`obj`/`dist`） |
| P2 | 安装 .NET 10 SDK：`winget install Microsoft.DotNet.SDK.10`（约 200MB，会弹一次 UAC） | **保留 7.0.410 不卸载**，这是回滚的前提；安装后 `dotnet --list-sdks` 应同时出现两者 |
| P3 | 建议加 `global.json` 先钉住 `7.0.410` 并提交 | 让"基线"可精确重现；迁移那一步只改这一个文件的 `rollForward`/版本，回滚就只是改回一个文件 |
| P4 | 记录迁移前基线 | 0 警告构建、49/49 测试、`dist` 三个二进制的 SHA256、`--diag` 输出各留一份 |

### 3.1 执行顺序（最小 diff 原则）

| # | 动作 | 通过判据 | 失败时 |
|---|---|---|---|
| S1 | `global.json` 的 SDK 版本改为 10.0.x | `dotnet --version` = 10.0.x | 改回即回滚 |
| S2 | 三处 TFM：`net7.0` → `net10.0`（Core、Tests）、`net7.0-windows` → `net10.0-windows`（App） | —— | 纯文本改动，可即时回退 |
| S3 | `dotnet clean` + `dotnet build FocusGuard.sln -c Release` | **0 警告 0 错误** | 见 §3.2，逐条处理；2 小时定位不了就回滚 |
| S4 | 全量测试 `dotnet run --project tests/FocusGuard.Tests -c Release` | **49/49 通过** | 失败项定位根因；不通过不进入下一步 |
| S5 | `dotnet publish ... -o dist` + 校验 | `dist` 与 `bin/Release` 三个二进制 SHA256 一致；图标 8 帧仍在 exe 中；关键文案存在性检查通过 | —— |
| S6 | CLI 冒烟：`FocusGuard.exe --diag`（只读） | 输出 `状态文件：可用`、`实际强制措施：无`、hosts 无区块 | —— |
| S7 | **WPF 手动验收 10 项**（按《验收与升级作业单.md》） | 全部通过 | 记录现象与日志，反馈后定位 |
| S8 | 更新文档（README / 设计方案 / 作业单里的 TFM 与运行时要求） | —— | —— |
| S9 | 合并回主分支；**至少保留 7.0.410 两到四周**再考虑卸载 | —— | —— |

**S1 与 S2 分开做**是有意的：如果 S3/S4 出问题，可以立刻分辨"是 SDK 的问题还是 TFM 的问题"。

### 3.2 可能的破坏性变更与应对

| 类别 | .NET 7 → 10 的变化 | 本项目是否受影响 | 应对 |
|---|---|---|---|
| **语言版本** | 默认 C# 11 → C# 14，新编译器/分析器可能报出新警告 | **可能**（本项目把 0 警告当门禁） | 逐条评估：真问题就修，误报就用注释说明原因后局部抑制；不允许整批压制 |
| **WPF** | .NET 9 起 WPF 引入新的 Fluent 主题（可选启用），默认主题行为未变 | 间接可能（本项目**全部使用自绘 ControlTemplate + 显式颜色**，不依赖默认主题细节） | S7 手动验收重点看：颜色、圆角观感、DPI 下的窗口尺寸 |
| **BCL 文件 IO** | `File.Replace` / `File.Move(overwrite:)` / `WriteAllBytes` / `GetFolderPath` 语义稳定 | 无 | D1–D4、B1 测试守住 |
| **`System.Text.Json`** | 跨版本有微调（转义、属性顺序等） | 低（只序列化自有 POCO，消费方也是自己） | F2/F3 往返测试守住 |
| **外部进程** | `icacls` / `ipconfig` / `whoami` 与 .NET 版本无关 | 无 | C/G 组测试守住 |
| **Windows 特定** | UAC manifest、apphost、`SpecialFolder.System` 行为稳定 | 无 | —— |
| **部署面** | 分发到其他机器需要 **.NET 10 桌面运行时**（本机已装 10.0.11） | **是**（换机器时） | 文档写明；或改自包含发布 |
| **状态/配置文件** | `state.json` / `config.json` 与 TFM 无关 | 无 | 无需迁移 |
| **SDK 行为** | `NETSDK1138` 警告消失；新 SDK 分析器更严格 | 可能（新警告） | 同语言版本项 |

### 3.3 依赖包与第三方库兼容性

- **零第三方 NuGet 依赖（实测证据见 §1.3）** → 这一类风险整体不存在，是本方案最确定的利好
- 唯一的外部依赖是 SDK 自带的 targeting pack 与 `Microsoft.WindowsDesktop.App` 共享框架 → 本机已有 10.0.11
- 测试宿主是自研的无依赖控制台 → 不存在 xunit/NUnit/MSTest 的版本升级连锁问题
- 未来若引入第三方包，需在引入时确认其 `net10.0` 支持，而不是留到下次迁移

### 3.4 测试与验证策略（六层，逐层放行）

| 层 | 内容 | 判据 | 不通过时 |
|---|---|---|---|
| L1 | 构建 | 0 警告 0 错误 | 逐条处理警告，禁止整批压制 |
| L2 | 49 项测试（纯逻辑 + 真实 icacls/文件系统集成） | 全部通过 | 定位根因后修复；这是迁移的门禁 |
| L3 | 发布一致性 | `dist` 三个二进制 SHA256 与 `bin/Release` 一致；图标 8 帧仍在 exe 中 | 查 publish 配置 |
| L4 | CLI 冒烟 | `--diag` 输出正常、hosts 无区块 | —— |
| L5 | **WPF 手动验收 10 项**（见作业单） | 全过 | 记录现象 + 日志，反馈定位 |
| L6 | 虚拟机硬断电（可选，独立事项） | —— | 不阻塞本次迁移 |

### 3.5 回滚方案

**触发条件**：S3–S7 任一层失败，且 2 小时内无法定位根因 → 回滚，问题另行处理。
回滚本身不承担"修好"的义务，先恢复可用基线。

| 场景 | 操作 |
|---|---|
| **首选（有 git）** | `git checkout main`（或 `git revert` 迁移提交）→ `dotnet clean` → 重建 → 49 项测试确认回到基线 |
| **无 git 时** | 解压迁移前的整目录备份（排除 `bin`/`obj`/`dist`）→ 同上重建验证 |
| **只回滚 SDK 选择** | 把 `global.json` 的版本改回 `7.0.410` → 重建（TFM 已是 net10 时**不能**只做这一步，必须连同 TFM 一起回） |
| **完整回滚（代码+TFM）** | 三处 TFM 改回 `net7.0` / `net7.0-windows` → `dotnet clean` → 重建 → 49/49 测试 → 重新 publish |
| **数据回滚** | 不需要。`state.json` / `config.json` / hosts 的形态与 TFM 无关 |
| **前提** | **7.0.410 必须保留**（这就是回滚能力本身），至少保留到迁移稳定后 2–4 周 |

### 3.6 风险评估矩阵

| 风险 | 概率 | 影响 | 缓解手段 |
|---|---|---|---|
| 新编译器/分析器产生新警告 | 中 | 低 | 0 警告门禁；逐条评估，禁止整批压制 |
| WPF 观感/行为差异 | 低 | 低 | 全部自绘模板 + 显式颜色；S7 手动验收确认 |
| 49 项测试出现回归 | 低 | 中 | 测试本身就是迁移门禁，先修再走 |
| 换机器分发缺运行时 | 中 | 中 | 文档写明需 .NET 10 桌面运行时；或改自包含发布 |
| 图标/资源嵌入变化 | 低 | 低 | publish 后做 8 帧存在性检查（现有流程已有） |
| 第三方包不兼容 | **不存在** | — | 零依赖（§1.3 实测） |
| 回滚不可用 | 低 | 高 | git init + 目录备份 + 保留 7.0.410 |
| 中断（断电等）导致半迁移 | 低 | 低 | TFM 是 3 处纯文本改动，重跑构建即可发现；无持久化副作用 |

**总体评价：低风险迁移。** 不确定性最集中的是 WPF 观感，靠"最小 diff + 手动验收"兜底；
最大的不确定来源（第三方依赖）恰好不存在。

### 3.7 工作量估算

| 阶段 | 耗时 |
|---|---|
| SDK 下载安装 | 10–20 分钟（取决于网速） |
| 代码改动（S1–S2） | **约 5 分钟，3 行** |

## 4. 如果想缓一缓：不迁的替代路径

| 路径 | 评价 |
|---|---|
| **A. 保持 net7.0，接受 EOL** | 可行，但要写进已知边界（当前文档已写）。问题不会恶化，也不会好转；每过一个大版本就要重新评估一次 |
| **B. 迁到 .NET 8 LTS** | **不推荐**：60 天后（2026-11-10）就到期，等于白做一次迁移还得再做一次 |
| **C. 迁到 .NET 9 STS** | 同 B，且 STS 支持期更短 |
| **D. 迁到 .NET 10 LTS（推荐）** | 支持到 2028-11-14；本机运行时已就位；零依赖使成本最低 |

**结论：要迁就直接迁 .NET 10，不要在 8/9 上停留。**
