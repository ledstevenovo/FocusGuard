# 验收与升级作业单

三件剩余事项的性质不同，先分清**谁做什么**：

| 事项 | 我能做 | 只能你做 | 为什么 |
|---|---|---|---|
| WPF 手动验收 | 提供逐项验收脚本、故障制造手法、取证命令 | **实际点击与观察** | 程序 manifest 要求提权，非交互环境会卡在 UAC 弹窗上，我无法驱动 GUI |
| 真实断电验证 | 给出可重复命中的方案与检查清单 | **准备可牺牲的机器/虚拟机并执行** | 我无法操作你的电源与虚拟机 |
| .NET 迁移 | 可以**代做**（装 SDK、改 TFM、重建、重测、重发布） | 授权安装系统级 SDK + 升级后重做一轮手动验收 | 安装 SDK 是系统级改动，我不会未经许可执行 |

## 一、WPF 手动验收（约 15 分钟）

### 准备

```powershell
cd D:\WorkBuddy\2026-09-13-19-39-17\FocusGuard
.\dist\FocusGuard.exe --diag          # 先留一份"干净状态"基线
```

双击 `dist\FocusGuard.exe`（会弹 UAC，选"是"）。

> 底部的两行状态是**实时探测**出来的，下面每一处的"预期"都以此为准。

### 1. 启动与初始状态

| 步骤 | 预期 |
|---|---|
| 双击运行 | 弹 UAC → 出现无边框圆角窗口，居中，按钮写着「开始专注」 |
| 观察底部 | `网站规则：未写入 hosts` + `FM 文件：未改名` |

### 2. 单实例保护

| 步骤 | 预期 |
|---|---|
| 再双击一次 `dist\FocusGuard.exe` | 弹提示「FocusGuard 已经在运行了」，随后自己退出；第一个窗口不受影响 |

### 3. 操作进行中禁止关闭（重要，能造出时间窗）

这个用**临时改配置**的办法最容易造出来：

| 步骤 | 预期 |
|---|---|
| 编辑 `%LOCALAPPDATA%\FocusGuard\config.json`，把 `"BlockedProcessNames"` 改成 `["notepad"]` | —— |
| 打开一个记事本（notepad.exe） | —— |
| 点「开始专注」 | 弹出询问框「检测到以下程序正在运行：notepad…」 |
| **别点询问框，先看窗口右上角** | ✕ 与 − 都已变淡（禁用态 45% 不透明度）—— `BeginBusy` 在弹框之前就把两个键一起禁掉了 |
| **再试着点 ✕ 或 −** | 两个都点不动。注意询问框是以本窗口为**属主的模态框**，Windows 会把本窗口的输入一并禁掉，所以这一刻点不动是双保险；计时上的忙碌窗口很短，"点不动"这件事靠肉眼手速很难稳定命中，**灰掉的外观才是可稳定观察的判据** |
| 回到询问框选「否」 | 窗口回到「开始专注」，底部仍是"未写入 hosts"；两个键恢复可用 |
| 把 `BlockedProcessNames` 改回 `["fm", "Berkelium"]` | —— |

> `OnClosing` 里那道「正在执行操作，请等它完成后再关闭」的拦截，只有在忙碌期间走 **Alt+F4 /
> 任务栏右键「关闭窗口」** 时才会触发 —— ✕ 本身在忙碌时已被禁用，`Click` 根本不会发出。
> 它是一道防御性保护，不必刻意去命中它。

### 4. 正常开始 / 结束

| 步骤 | 预期 |
|---|---|
| 点「开始专注」 | 按钮变「结束专注」；窗口整体转深蓝；底部变 `网站规则：已写入 hosts（20 个域名）` + `FM 文件：已改名为 fm.exe.focusguard-locked`；按钮下方出现 `已专注 00:00:xx` |
| 浏览器分别打开 知乎 / 虎扑 / YouTube / B 站 | 均打不开（可能显示"无法访问此网站"） |
| 双击 `D:\11Player-FM2012_1204\fm.exe`（或桌面快捷方式） | 提示找不到文件 / 无法打开 |
| 点「结束专注」 | 按钮回到「开始专注」；窗口变浅；底部变 `网站规则：未写入 hosts` + `FM 文件：未改名` |
| 再刷新四个网站 | 恢复正常 |
| 再看 `D:\11Player-FM2012_1204\` | `fm.exe` 名字已恢复 |

### 5. 每秒刷新（冲突检测）

| 步骤 | 预期 |
|---|---|
| 点「开始专注」 | 锁定成功 |
| 在资源管理器里把 `fm.exe.focusguard-locked` **复制**一份到同目录，改名为 `fm.exe` | 制造"两份同时存在" |
| 盯着底部状态（不要点任何按钮） | **1 秒内**变成 `FM 文件：原文件与锁定文件同时存在，需手工确认` |
| 点「结束专注」 | 弹出失败提示；窗口保持锁定；**两份文件都还在，没有被覆盖或删除** |
| 删掉你复制出来的那份 `fm.exe`，再点「结束专注」 | 成功，全部恢复 |

### 6. 部分解除失败 + 重试（重要）

用测试里同一个"人为制造故障"手法，确定有效：

| 步骤 | 预期 |
|---|---|
| 点「开始专注」 | 锁定成功 |
| 打开 `C:\Windows\System32\drivers\etc`，**新建一个文件夹**，名字正好是 `hosts.focusguard.tmp` | —— |
| 点「结束专注」 | 弹「以下步骤失败…」；窗口**保持锁定**；底部出现 `恢复失败：移除 hosts 规则` |
| 删掉那个文件夹，再点「结束专注」 | 这次成功，全部恢复 |

### 7. 未定位记录的三选一

| 步骤 | 预期 |
|---|---|
| 点「开始专注」 | 锁定成功 |
| 把 `fm.exe.focusguard-locked` 移到别处（比如桌面） | —— |
| 点「结束专注」 | hosts 被清掉，但会提示「记录显示曾把文件改名为…找不到它…已保留这条记录线索」；底部显示 `FM 文件：记录中的锁定文件未找到（…）` |
| 再点「开始专注」 | 弹出三选一：**是** = 再试一次恢复 / **否** = 放弃这条记录并开始 / **取消** = 什么都不做 |
| 先选「取消」 | 什么都没发生 |
| 再点「开始专注」选「是」 | 再试一次恢复，仍找不到 → 保持原状并给出提示 |
| 再点「开始专注」选「否」 | 记录被放弃（写进日志），随后正常开始专注 |
| 最后点「结束专注」并确认工作目录干净 | 全部恢复 |

### 8. 强杀恢复

| 步骤 | 预期 |
|---|---|
| 点「开始专注」 | 锁定成功 |
| 任务管理器里结束 `FocusGuard.exe` | 进程消失（锁仍在生效） |
| 重新双击 `dist\FocusGuard.exe` | 界面直接显示「结束专注」，底部提示「检测到限制仍在生效（上次可能异常退出）」 |
| 点「结束专注」 | 全部恢复，`fm.exe` 回来 |

### 9. 退出确认

| 步骤 | 预期 |
|---|---|
| 点「开始专注」→ 点 ✕ → 选「否」 | 窗口不关，仍在专注中 |
| 再点 ✕ → 选「是」 | 先解除限制，然后退出；检查 `fm.exe` 已恢复 |

### 10. 窗口最小化（本次新增）

窗口是无边框 + 透明背景（`WindowStyle=None` + `AllowsTransparency=True`），最小化/还原的渲染只能实机看。

| 步骤 | 预期 |
|---|---|
| 观察标题栏 | ✕ 左边有一个 `−`，两键同色同尺寸、水平对齐；`−` 不要明显地偏上/偏下（若偏，见下方"不通过时"） |
| 未专注时点 `−` | 窗口收进任务栏；点任务栏图标能还原，**窗口仍是圆角、无黑块/无残影** |
| 点「开始专注」，专注中再点 `−` 并还原 | 仍然可用，还原后仍是深蓝专注态、`已专注` 计时连续（不归零） |
| 专注中最小化后，双击 `D:\11Player-FM2012_1204\fm.exe` | 仍然打不开（最小化不影响强制手段） |
| 专注中最小化 → 从任务栏还原 → 点「结束专注」 | 正常解除，`fm.exe` 恢复 |

## 二、真实断电验证

### 为什么现有测试不能替代

E8 / E9 模拟的是**代码执行到某处被打断**（进程消失），而断电还会带来**文件系统层面的半写**风险。
我们用「先写临时文件、再整体替换」把窗口压到一次 rename；NTFS 的 rename 是元数据操作、通常由日志保证原子性 ——
但这是**推论，不是证据**。所以文档里这条一直标注为"未验证"。

### 唯一能精确命中的做法：虚拟机硬断电

`Stop-VM -TurnOff`（Hyper-V）或 `VBoxManage controlvm <vm> poweroff`（VirtualBox）是**立即断电**，
不是正常关机，可以在任意时刻命中。

1. 准备一台 Windows 虚拟机（Hyper-V 需 Windows 11 专业版；VirtualBox / VMware 不限版本）
2. 把 `dist\` 整个目录拷进虚拟机，管理员运行 `FocusGuard.exe`（首次运行会创建配置与状态）
3. 点「开始专注」，**在操作进行中的那一瞬间**执行硬断电

   时间窗很短（几百毫秒）。提高命中率的办法：在虚拟机里给 hosts 造一个很大的初始文件（比如先手动
   往 hosts 里追加几千行注释），让写入耗时变长，再反复试几次。

4. 重启虚拟机后逐项检查：

| 检查项 | 通过判据 | 命令 |
|---|---|---|
| hosts 是否仍可解析 | 网络正常，没有语法错误 | `type C:\Windows\System32\drivers\etc\hosts` |
| 有没有半截的屏蔽块 | `--diag` 报告 `hosts 屏蔽区块：存在/不存在`，且**不存在**只有 BEGIN 没有 END 的情况 | `.\FocusGuard.exe --diag` |
| 状态文件是否可解析 | `--diag` 显示 `状态文件：可用`，或明确报"缺失或损坏" | 同上 |
| FM 文件名是否正常 | 要么是 `fm.exe`，要么是 `fm.exe.focusguard-locked`，**不能两个都存在、也不能都缺失** | `dir "D:\11Player-FM2012_1204\fm*.exe*"` |
| 能否清干净 | 点「结束专注」或 `--unlock` 后，四个网站恢复、`fm.exe` 回来 | —— |

5. 建议两个中断点各试 3 次：**改名前**（意图已落盘）、**改名后**（确认未写）、**hosts 写入中**。

### 如果不方便做

那就保持"未验证"的标注，依靠 E8/E9 + NTFS 原子 rename 的推论。**这条不建议我替你写成已验证** ——
没有证据就不该那么写。

## 三、.NET 迁移（建议独立一次搞定）

> 完整的分析、破坏性变更清单、风险矩阵与回滚细节见
> **[docs/dotnet10-迁移分析与方案.md](docs/dotnet10-迁移分析与方案.md)**。
> 以下是执行摘要，与该文档的 §3.1 六层验证一一对应。

### 为什么不能只靠"没有版本相关 API"

这句话只能说明**编译期**风险低，覆盖不了：
- WPF 在 .NET 8/9/10 上的渲染与 DPI 细节变化
- apphost / manifest 提权行为差异
- 目标机器必须有对应的**桌面运行时**（本机已装 10.0.11，但换机器就要装）

所以升级必须走完整的「改 → 建 → 测 → 发布 → 手动验收」。

### 步骤（每步都有判据）

| # | 动作 | 通过判据 |
|---|---|---|
| 0 | 确认 git 基线：`main` 上已有提交（bin/obj/dist 已被 `.gitignore` 正确排除）；**把未跟踪的 `docs/` 补提交**；建 `migration/net10` 分支；记录迁移前基线（0 警告构建 / 49 项测试 / `--diag` 输出） | `git status` 干净 |
| 1 | 安装 .NET 10 SDK（LTS，支持到 **2028-11-14**）：`winget install Microsoft.DotNet.SDK.10`（约 200MB，会弹一次 UAC） | `dotnet --list-sdks` 同时出现 `7.0.410` 与 `10.0.401`；`dotnet --list-runtimes` 出现 Desktop **10.0.12**（SDK 自带，与已有的 10.0.11 共存）；**保留 7.0.410 不卸载** |
| 2 | 新建 `global.json`：`{ "sdk": { "version": "10.0.401", "rollForward": "latestPatch", "allowPrerelease": false } }`（**必须写完整版本号，不支持 `10.0.x` 通配符**；SDK 号 10.0.401 与运行时号 10.0.12 是两套，别混） | `dotnet --version` = `10.0.401` |
| 3 | 改 **4 处**：三个 csproj 的 TFM（`net7.0`→`net10.0`、`net7.0-windows`→`net10.0-windows`）**+ `.github/workflows/release.yml` 的 `dotnet-version: 7.0.x` → `10.0.x`**（漏了它，打标签发版时 CI 必挂） | —— |
| 4 | **删除所有 `bin/`、`obj/`、`dist/`**（TFM 变了，`dotnet clean` 清不掉旧 `net7.0` 的输出目录）→ `dotnet restore` + `dotnet build FocusGuard.sln -c Release` | **0 警告 0 错误**（新警告逐条处理，禁止整批压制） |
| 5 | 全量重跑测试 | **49/49 通过**。有失败就逐项查，不能跳过 |
| 6 | 删掉旧 `dist/`，重新 `dotnet publish src/FocusGuard.App -c Release -o dist`（**保持框架依赖形态不变，不要顺手改自包含**） | **功能性验证**：`dist\FocusGuard.runtimeconfig.json` 里 TFM=`net10.0` 且依赖 `Microsoft.WindowsDesktop.App 10.x`；`FocusGuard.Core.dll` 在；图标 8 帧仍在 exe 中；`dist\FocusGuard.exe --diag` 正常 |
| 7 | CI 验证：打一个测试标签（或临时改 workflow 只跑 build 不发版），确认 Actions 上 .NET 10 构建通过 | CI 绿 |
| 8 | **重做第一部分的全部手动验收** | 10 项全过 |

**迁移纪律**：迁移提交里**不要顺手使用 C# 14 新语法**（`field`、`extension`、集合表达式等）——
否则出 Bug 时分不清是框架迁移问题还是代码重构问题。验收时应看到 git diff 只包含
3 个 csproj、1 个 workflow、`global.json` 和相关文档。

### 风险控制

- **独立分支/独立提交**，不要和功能改动混在一起，便于整体回滚
- 回滚方法：三处 TFM 改回 `net7.0` / `net7.0-windows` + workflow 改回 `7.0.x` + 删掉 `global.json` →
  删除 `bin`/`obj`/`dist` → 重建 → 49 项测试确认回到基线
- **7.0.410 至少保留 2–4 周**，确认迁移稳定后再考虑卸载
- 若第 5 步出现与 WPF 相关的失败，先在 `net8.0-windows` 上试一次，缩小范围
- **不要迁到 .NET 8 / 9**：两者都在 2026-11-10 结束支持，迁过去等于 60 天后再迁一次
- 本地 `dist` 保持框架依赖、CI 保持自包含——**本次迁移不改发布形态**，一次只改一个变量
