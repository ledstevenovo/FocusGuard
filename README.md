# FocusGuard

Windows 11 上的极简专注工具。界面上只有一个按钮：

- 点 **开始专注** → 知乎 / 虎扑 / YouTube / 哔哩哔哩 打不开，FM 也启动不了
- 点 **结束专注** → 全部恢复原状

设计取舍是**防自己手滑，不对抗蓄意绕过**：不做常驻监控、不做篡改检测、被任务管理器杀掉也没关系。
第一位的原则是：**宁可被绕过，也不能出现「限制解不干净」。**

---

## 快速开始

```bash
dotnet build FocusGuard.sln -c Release
dotnet publish src/FocusGuard.App/FocusGuard.App.csproj -c Release -o dist
```

双击 `dist\FocusGuard.exe` 即可（**会弹一次 UAC**，因为要改 hosts 文件）。

| 命令行参数 | 作用 |
|---|---|
| 无 | 打开窗口 |
| `--unlock` | 解除能探测到的全部限制（不看配置） |
| `--unlock "D:\某个目录"` | 在指定目录里查找并还原被改名的文件 |
| `--discard-record` | 确认后放弃一条未能定位的记录线索（会先要求确认） |
| `--remove-legacy-deny` | 显式移除旧版本留下的 icacls 拒绝规则 |
| `--diag` | 只读自检，结果写到 `diag-report.txt` |

## 它到底改了什么

只有两件事，都可逆、都不涉及任何权限位：

| 动作 | 具体内容 | 恢复方式 |
|---|---|---|
| 写入网站规则 | 往 `C:\Windows\System32\drivers\etc\hosts` 追加一段被 `# FocusGuard BEGIN/END` 包裹的区块（20 个域名，每个域名同时写 IPv4 + IPv6），然后 `ipconfig /flushdns` | 只删除自己那一段，区块外一字节不碰 |
| 阻止 FM 启动 | 把 `D:\11Player-FM2012_1204\fm.exe` 改名为 `fm.exe.focusguard-locked` | 改名回去 |

**它不动文件权限。** 早期版本用 `icacls /deny` 拦截，但解除只能用 `/remove:d`，会连带删掉该用户在此文件上的**全部**拒绝规则，可能放宽原有权限。改名只动文件名，天然可逆、天然幂等，残留状态一眼可见 —— 就算 FocusGuard 被删了，你在资源管理器里把文件名改回来就行。

hosts 首次被改动前会生成带时间戳的原始备份，写入后**回读校验**；hosts 本身用原子替换写入，**不会重建文件**（原有 ACL 与创建时间都保留），也没有"退回覆盖写入"的兜底 —— 写不进去就直接报错。

```
┌──────────────────────────────┐

│                              │
│        ┌────────────┐        │
```

- 专注中窗口整体转深蓝，按钮变「结束专注」
- 窗口无边框，按住任意位置可拖动，右上角 ✕ 关闭

## 出问题时的行为（重要）

这套设计把「限制解不干净」当头号风险，所以下面几条是刻意做成这样的：

1. **记录存不下来就不动手。** 开始专注的第一步是把"我准备改什么"写进状态文件；写失败会**立即中止**，
   hosts 与文件改名一步都不做 —— 不会出现"改了名却没有恢复线索"的局面。
2. **解除失败不会显示成功。** 只有部分项失败时，已成功的项照常回滚，失败的项被记录下来，界面显示
   「部分解除失败：…」并保持锁定态，处理完原因可以直接重试。
3. **找不到的不会当成没发生。** 如果记录显示曾锁定某个文件、但现在定位不到它，会明确报警，
   **并保留这条记录线索不清空**，界面持续显示"记录中的锁定文件未找到"，同时提示用 `--unlock <目录>` 补救。
   （不会因为"hosts 那边成功了"就把 FM 这边的问题掩盖过去。）
4. **已经恢复的不会被误报。** 判定"是否已恢复"看的是那个目标文件自己的状态（原文件在位、没有锁定文件），
   而不是"在别处找不到锁定文件" —— 后者本来就是已恢复的正常结果。
5. **不会覆盖还没解决的旧线索。** 如果上一条记录仍未能定位，点「开始专注」不会直接开始，而是弹三选一：
   再试一次恢复 / 放弃这条记录并开始 / 取消。只有你明确选择放弃，程序才会丢掉那条线索（并写进日志）。
6. **同名不等于同一个文件。** 用 `--unlock <目录>` 补救时，程序会照常还原该目录里找到的锁定文件，
   但只有**恢复路径与记录路径完全一致**才清空记录。路径不同（哪怕文件名一模一样）就保留线索，
   并把**原记录路径和本次恢复路径都列出来**让你核对；确认对应后用 `--discard-record`（或界面上
   选择"放弃这条记录"）清除它。「放弃记录」如果写盘失败会如实报错，不会出现"说已放弃、重启后又冒出来"。
7. **专注中关闭窗口会先问一句**，确认后先解除再退出；**解除失败就取消退出**，把窗口留下让你重试。
8. **操作进行中无法关闭、也无法再次点击。** 互斥范围从点击那一刻开始，覆盖「弹窗确认 → 结束进程 →
   锁定/解除」整段流程，不会出现两次操作交错。
9. **不会多开。** 重复启动会提示已在运行并退出；单实例保护覆盖整个进程生命周期。
10. **被强杀也没关系。** 重启程序会自动识别残留并显示「结束专注」+「限制生效中」，点一下清干净。
11. **改过配置也能解锁。** 即使你改了游戏路径、或关掉了锁定开关，程序仍会按落锁时记录的对象还原。
12. **不会覆盖或删除任何文件。** 如果 FM 被更新程序重新生成，出现「原文件 + 锁定文件同时存在」的冲突，
    程序会**拒绝操作**并把两份文件的路径都告诉你。

## 配置

`%LOCALAPPDATA%\FocusGuard\config.json`（首次运行自动生成）：

```json
{
  "BlockedDomains": [ "zhihu.com", "www.zhihu.com", "..." ],
  "BlockedProcessNames": [ "fm", "Berkelium" ],
  "TargetExe": "D:\\11Player-FM2012_1204\\fm.exe",
  "LockTargetExe": true,
  "RecoveryDirectories": [],
  "ShowElapsed": true
}
```

| 字段 | 说明 |
|---|---|
| `BlockedDomains` | 要屏蔽的域名清单，改完重启程序生效 |
| `BlockedProcessNames` | 开始专注时若在运行，会弹窗询问后结束它们 |
| `TargetExe` | 要阻止启动的程序 |
| `LockTargetExe` | 设为 `false` 则只写 hosts，完全不动那个程序文件 |
| `RecoveryDirectories` | 补充的恢复搜索目录，只在状态丢失且目标路径被改过时用得上 |
| `ShowElapsed` | 是否在按钮下方显示已专注时长 |

其他路径：

- 日志：`%LOCALAPPDATA%\FocusGuard\focusguard.log`
- 状态：`%LOCALAPPDATA%\FocusGuard\state.json`
- 自检报告：`dist\FocusGuard.exe --diag`

## 关于旧版本

如果你用过更早的版本（用 `icacls /deny` 拦截 FM 的版本），文件上可能残留一条拒绝规则，它会让改名失败。
程序会**检测到并提示**，但**不会自动去动它** —— 因为旧版本没有保存原始 ACL，移除只能靠 `/remove:d`，
那会删掉该用户在这个文件上的全部拒绝规则，无法精确还原。

确认要清理时执行：

```
dist\FocusGuard.exe --remove-legacy-deny
```

## 已知边界

1. 浏览器开启「安全 DNS / DoH」时会绕过 hosts —— 关掉浏览器的安全 DNS 即可。这是不引代理的固有代价。
2. 开始专注前已打开的页面可能短暂仍能访问（浏览器缓存），刷新即失效。
3. 需要管理员权限，每次启动弹一次 UAC。
4. 管理员可以手工改 hosts 或把文件名改回去绕过 —— 这是防御模型的天花板。
5. 只拦桌面端浏览器与 exe 启动，不拦手机、不拦其他设备。
6. 中断恢复用"崩溃窗口"测试覆盖（已改名未写确认 / 已写意图未改名），**未做真实断电测试**；
   状态文件"写临时文件再替换"在方向上正确，但没有证明真实断电下的数据完整性。
7. **未实测 WPF 窗口交互**：manifest 要求提权，非交互环境会卡在 UAC 弹窗上。请你双击跑一次。
8. 权限验证的边界：测试比较的是 **DACL**（`icacls` 输出 + `icacls /save` 导出），**不含所有者、组与 SACL**。
9. **已迁移到 .NET 10 LTS**（2026-09-14）：SDK 10.0.401（`global.json` 钉住），目标框架
   `net10.0` / `net10.0-windows`，运行时依赖 `Microsoft.WindowsDesktop.App` 10.x。
   分发到其他机器需要先装 .NET 10 Desktop Runtime；发布形态保持框架依赖，未改自包含。
   迁移依据与过程见 docs/dotnet10-迁移分析与方案.md；WPF 手动验收仍待执行。


## 测试

```bash
dotnet run --project tests/FocusGuard.Tests -c Release
```

54 项全部跑在临时目录上，包含真实验证而非假设：

- **状态写不下时开始必须中止**，且 hosts 与文件都没被动过
- **记录中的目标找不到时报警并保留线索**，路径完全一致地恢复后才清空
- **存在未定位记录时开始被拒绝**，旧线索不会被覆盖；目录恢复无关文件也不会清空旧线索
- **跨目录遇到同名文件时保留线索，并把原记录路径与本次恢复路径都列出来**
- **已恢复的目标在重试时不会被误报为未找到**；放弃记录落盘失败会报错并还原内存记录
- 改名锁定/解锁后内容逐字节一致；**冲突时两份文件都不被覆盖或删除**
- **权限保留验证**：比较完整 `icacls` 输出 + `icacls /save` 导出的 **DACL** + 创建时间（不含所有者与 SACL）
- **失败路径验证**：在目标路径上放同名目录以确定性制造写入失败，断言不谎报成功、失败项被保留、重试可成功
- 崩溃在「已改名未确认」与「已写意图未改名」两个阶段，重启后都能正确处理
- 状态文件丢失 + 配置路径改变时明确报告定位不到，并可用 `--unlock <目录>` 补救
- 不破坏 hosts 原有 GBK 字节

`dotnet publish` 后会用 SHA256 对比 `dist/` 与 `bin/Release/` 的产物，并检查成品内含最新文案，
避免"改了源码但成品是旧的"。

## 发布

版本发布由 GitHub Actions 自动完成：给要发布的提交打上 `v` 开头的标签并推送即可。

```bash
git tag v1.5.0
git push origin v1.5.0
```

Actions 会在托管的 Windows 环境执行与「快速开始」相同的构建命令，再做一步自包含发布
（`-r win-x64 --self-contained true`，标签中的版本号经 `-p:Version` 注入成品），
打包为 `FocusGuard-v<版本>-win-x64.zip`（不含 pdb），自动创建 Release 并上传附件。
本地 `dotnet publish -o dist` 流程不受任何影响。
